  A. GESTIÓN DE USUARIOS DEL PANEL
───────────────────────────────────────────────────────────────────

  A-1. CAMBIAR LA CONTRASEÑA DEL ADMIN
  ─────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN.

  Pasos:
    1. Iniciar sesión en el panel con la cuenta superadmin.
    2. Ir a la pestaña Configuración.
    3. Buscar la sección de credenciales / cambio de contraseña.
    4. Escribir la nueva contraseña para el usuario "admin".
       REQUISITO: mínimo 8 caracteres (el servidor rechaza menos).
    5. Confirmar.

  Respuesta esperada:
    - El panel muestra un mensaje de éxito.
    - La próxima vez que "admin" ingrese, debe usar la nueva contraseña.
    - El token actual de "admin" sigue válido hasta que expire (8 horas),
      es decir: si "admin" ya estaba logueado, sigue logueado hasta cerrar
      sesión o que el token expire.

  Si algo falla:
    - "Contraseña muy corta": el servidor exige 8 caracteres mínimo.
      El panel muestra el error del servidor.
    - Sin respuesta: verificar que el servidor esté corriendo.


  A-2. CAMBIAR LA CONTRASEÑA DEL SUPERADMIN
  ───────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN (cambia su propia contraseña).

  Pasos: igual que A-1 pero seleccionando el usuario "superadmin".

  PRECAUCIÓN: si olvidás la nueva contraseña, ver A-3.


  A-3. QUÉ PASA SI OLVIDÁS LA CONTRASEÑA
  ─────────────────────────────────────────
  ACLARACIÓN: NO hay que resetear la base de datos completa. Solo hay
  que actualizar UN campo (password_hash) en la tabla "usuarios". Los
  datos de alumnos, sesiones, historial, etc. no se tocan.

  No hay recuperación automática (sin email de reset). Hay que actualizar
  el hash directamente en la base de datos.

  Pasos (requiere acceso a la PC del servidor):
    1. Abrir una terminal en la PC del servidor (CMD o PowerShell).
    2. Conectarse a MySQL:
         mysql -u root -pimpo2010 biblioteca_unasam
    3. Generar un hash bcrypt de la nueva contraseña con Python:
         python -c "from passlib.context import CryptContext; ctx=CryptContext(schemes=['bcrypt']); print(ctx.hash('NuevaContraseña123'))"
       Esto imprime algo como: $2b$12$abcdef...
    4. Actualizar en MySQL (pegar el hash generado):
         UPDATE usuarios SET password_hash='$2b$12$...' WHERE username='superadmin';
    5. Listo. No hace falta reiniciar el servidor.

  Respuesta esperada:
    - El usuario puede iniciar sesión con la nueva contraseña.

  PENDIENTE (mejora): Agregar un campo en Configuración para que el
  superadmin pueda cambiar su propia contraseña desde el panel, sin
  tener que entrar a la base de datos. (Registrado en MEJORAS abajo.)


  A-4. LA SESIÓN DEL PANEL EXPIRÓ (401 UNAUTHORIZED)
  ─────────────────────────────────────────────────────
  El token JWT del panel tiene validez de 8 horas. Al expirar, todas
  las requests al servidor devuelven 401 y el panel cierra la sesión
  automáticamente.

  Síntomas en los logs del servidor:
    "GET /api/dashboard/stats HTTP/1.1" 401 Unauthorized
    "GET /api/terminales HTTP/1.1" 401 Unauthorized
    ... (varios endpoints en cadena)
    "Panel admin desconectado"

  Qué hacer:
    - Volver a iniciar sesión en el panel con usuario y contraseña.
    - El panel guarda el nuevo token y retoma el monitoreo normalmente.

  Nota: esto es comportamiento CORRECTO y esperado, no es un error.
  Los kioscos y las PCs de alumnos NO se ven afectados cuando expira
  el token del panel. Solo pierde acceso el navegador del admin.


───────────────────────────────────────────────────────────────────
  B. GESTIÓN DE ALUMNOS Y ACCESO
───────────────────────────────────────────────────────────────────

  B-1. REGISTRAR UN ALUMNO NUEVO
  ────────────────────────────────
  Quién puede hacerlo: admin y superadmin (importar masivo: solo superadmin).

  Opción 1 — Un alumno solo:
    1. Ir a pestaña Base de Datos → Estudiantes.
    2. Clic en "Nuevo".
    3. Completar: DNI (8 dígitos), nombre, apellidos, código, facultad,
       escuela.
    4. Guardar.

  Respuesta esperada:
    - El alumno aparece en la lista de estudiantes.
    - Puede usar una terminal inmediatamente.

  Opción 2 — Importar desde Excel (masivo):
    1. Preparar el Excel con columnas: dni, nombre, código, facultad,
       escuela (ver el formato en el template que ofrece el panel).
    2. Ir a Base de Datos → Estudiantes → Importar.
    3. Subir el archivo.

  Respuesta esperada:
    - El panel muestra cuántos registros se importaron / cuántos fallaron.
    - Los alumnos importados ya pueden usar las terminales.


  B-2. BANEAR A UN ALUMNO
  ─────────────────────────
  Quién puede hacerlo: admin y superadmin.

  Pasos:
    1. Ir a pestaña Alertas → Baneados.
    2. Clic en "Nuevo ban".
    3. Escribir el DNI del alumno y el motivo.
    4. Confirmar.

  Respuesta esperada:
    - El alumno aparece en la lista de baneados.
    - Si intenta usar una terminal, el kiosco muestra: "DNI baneado.
      Acérquese al módulo."
    - Si ya tenía una sesión activa, NO se cierra automáticamente.
      El ban aplica al próximo intento de login.

  SOBRE EL BAN Y EL PANEL ADMIN: el ban solo aplica al uso de
  terminales (kioscos). Los usuarios del panel (admin/superadmin) se
  gestionan por separado en la tabla "usuarios" y NO están sujetos al
  sistema de bans de alumnos. Son dos sistemas distintos: los bans
  son para alumnos que usan las PCs, no para administradores del panel.

  PENDIENTE (mejora): registrar quién aplicó el ban y cuándo, para
  tener trazabilidad. (Ver sección MEJORAS abajo.)


  B-3. LEVANTAR EL BAN DE UN ALUMNO (MANUALMENTE)
  ──────────────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN.

  Pasos:
    1. Ir a Alertas → Baneados.
    2. Buscar al alumno por DNI o nombre en la lista de bans activos.
    3. Clic en "Levantar ban".
    4. Confirmar.

  Respuesta esperada:
    - El ban queda marcado como levantado (fecha_fin = ahora).
    - Se registra quién lo levantó (levantado_por = username del superadmin)
      y a qué hora (fecha_levantado). Esto ya ocurre en el servidor.
    - El alumno desaparece de la lista de bans activos.
    - Puede volver a usar las terminales de inmediato.
    - Sus incidencias activas quedan reseteadas.
    - En el historial de bans (B-6 — pendiente), el registro seguirá
      visible con "Levantado por: <superadmin>" y la fecha.

  Diferencia con expiración automática:
    - Cuando el superadmin levanta el ban: levantado_por = "<username>"
    - Cuando el ban expira solo por fecha: levantado_por queda NULL
      (el sistema simplemente dejó de considerar el ban como activo)


  B-5. VER EL HISTORIAL DE BANS DE UN ALUMNO ESPECÍFICO
  ────────────────────────────────────────────────────────
  Caso de uso: quiero saber cuántas veces fue baneado un alumno, quién
  lo baneó cada vez, y cómo terminó cada ban.

  Pasos:
    1. Ir a Alertas → Baneados.
    2. Clic en "Historial" (botón junto a "Activos").
    3. Escribir el DNI del alumno en el filtro "DNI alumno".

  Respuesta esperada:
    - Lista de todos los bans del alumno (activos, expirados, levantados).
    - Por cada ban:
        * Fecha de inicio
        * Fecha de expiración original
        * Motivo
        * Baneado por: <username>
        * Estado:
            - "Activo"                    → fecha_fin en el futuro
            - "Expirado (sistema)"        → fecha_fin ya pasó, sin levantado_por
            - "Levantado por <username>"  → levantado_por presente


  B-6. VER TODOS LOS BANS — HISTORIAL GLOBAL
  ─────────────────────────────────────────────
  Caso de uso: el superadmin quiere auditar todos los baneamientos y
  desbanamientos del sistema (quién baneó a quién, cuándo, cómo terminó).

  Pasos:
    1. Ir a Alertas → Baneados.
    2. Clic en "Historial".
    3. Usar el filtro "Estado" para acotar: Todos / Activos /
       Expirados (sistema) / Levantados (admin).

  Respuesta esperada:
    - Tabla paginada con todos los bans, no solo los activos.
    - Columnas: Alumno, DNI, Motivo, Fecha inicio, Fecha fin original,
      Baneado por, Estado, Levantado por, Fecha levantado.
    - Filtros: por alumno/DNI, por fecha, por quién baneó, por estado.
    - Tres tipos de registros:
        1. ACTIVO          → fecha_fin en el futuro, levantado_por NULL
        2. EXPIRADO SISTEM → fecha_fin ya pasó, levantado_por NULL
        3. LEVANTADO ADMIN → levantado_por = "<username>", fecha_levantado presente


  B-4. DESBLOQUEAR MANUALMENTE UNA PC PARA UN ALUMNO
  ────────────────────────────────────────────────────
  Caso de uso: el alumno no puede escribir su DNI (problema técnico) o
  el admin quiere habilitar una PC para alguien en particular.

  Pasos:
    1. Ir a pestaña Nodos (monitoreo).
    2. En la tarjeta de la PC a desbloquear, clic en "Desbloquear".
    3. Se abre un modal: escribir el DNI del alumno y el motivo de uso.
    4. Confirmar.

  Respuesta esperada:
    - El servidor valida al alumno (ban, existencia en el maestro).
    - La PC muestra "Bienvenido, <nombre>" y se desbloquea.
    - En el panel, la tarjeta de esa PC cambia de estado a "activo"
      (indicador verde con el nombre del alumno).
    - Se registra una sesión en el historial.

  Si el DNI no existe en el maestro:
    - El servidor devuelve error y la PC sigue bloqueada.
    - El panel muestra el motivo del rechazo.

  C. CONTROL DE TERMINALES
───────────────────────────────────────────────────────────────────

  C-1. BLOQUEAR UNA PC DESDE EL PANEL
  ──────────────────────────────────────
  Pasos:
    1. En Nodos, clic en "Bloquear" en la tarjeta de esa PC.
    2. Confirmar en el diálogo.

  Respuesta esperada:
    - Si había sesión activa: se cierra (motivo interno "bloqueo_admin")
      y se registra la hora de salida automáticamente.
    - El kiosco vuelve a la pantalla de login bloqueada.
    - La tarjeta en el panel cambia a estado "bloqueado".
    - El historial guarda la sesión con hora de inicio y hora de cierre.
    - El admin NO tiene que escribir un motivo al bloquear: la acción
      en sí es el motivo (bloqueo manual por el administrador).

  SOBRE EL MOTIVO DE CIERRE: el motivo "bloqueo_admin" se guarda
  internamente en la BD para trazabilidad. Actualmente no se muestra
  en la interfaz de historial (solo se guarda). Si en el futuro se
  quiere mostrar el motivo de cierre en el historial, es un cambio
  de visualización, no de lógica.
  * el historial de quien bloquea desde el panel, ya sea el admin o superadmin debe de guardarse en la base de datos *


  C-2. APAGAR UNA PC DE FORMA REMOTA
  ─────────────────────────────────────
  Pasos:
    1. En Nodos, clic en "Apagar" en la tarjeta de esa PC.
    2. Confirmar.

  Respuesta esperada:
    - Se cierra la sesión activa (si había una).
    - La PC ejecuta apagado de Windows.
    - La tarjeta desaparece del mapa de PCs (pasa a "offline").
    - NOTA: si la PC no está conectada al servidor, el comando no llega
      y la PC no se apaga (no hay magia sin conexión).


  C-3. BLOQUEAR TODAS LAS PCS A LA VEZ
  ──────────────────────────────────────
  Pasos:
    1. En Nodos, buscar el botón "Bloquear sala" (bloqueo global).
    2. Confirmar (pide confirmación por ser una acción masiva).

  Respuesta esperada:
    - Se cierran todas las sesiones activas con hora de salida actual.
    - Se envía la orden de bloqueo a TODAS las terminales conectadas.
    - Las tarjetas del panel cambian a "bloqueado".
    - El historial registra el cierre de todas las sesiones.
    - Las PCs offline (desconectadas) NO reciben la orden. Al reconectar,
      el servidor las registra como "bloqueado" (pantalla de login), no
      como "activo" — el modo offline protege la sesión EN CURSO, no
      reinicia una sesión nueva. Esto es el comportamiento correcto.

  PENDIENTE: no hay botón de "Apagar todas" todavía.


  C-4. QUÉ PASA SI UNA PC SE DESCONECTA
  ──────────────────────────────────────────
  Desconexión con sesión activa:
    - El servidor detecta la caída del WebSocket.
    - Cierra la sesión (motivo "desconexion_red") y registra la hora.
    - Marca la terminal como "offline" en el panel.

  El kiosco del lado cliente:
    - Muestra un contador de 3 minutos intentando reconectar.
    - Si reconecta antes de 3 min Y tenía sesión activa en modo offline:
      la sesión se sincroniza con el servidor (/api/offline-sync) y
      continúa como activa.
    - Si no reconecta en 3 min: bloquea la pantalla.

  En el panel:
    - La tarjeta de esa PC aparece en estado "offline" (gris).
    - Cuando la PC vuelve a conectarse, el servidor la registra como
      "bloqueado" y la tarjeta vuelve al mapa activo.

  NOTA: varios comportamientos de C-4 (especialmente la reconexión
  con sesión offline activa) están implementados pero pendientes de
  prueba exhaustiva en condiciones reales.

  D. HISTORIAL Y SESIONES
───────────────────────────────────────────────────────────────────

  D-1. BUSCAR LAS SESIONES DE UN ALUMNO
  ──────────────────────────────────────
  Pasos:
    1. Ir a pestaña Historial.
    2. En el buscador, escribir el DNI o el nombre del alumno.
    3. Aplicar filtro de período si querés acotar (hoy / este mes /
       este año / todo).

  Respuesta esperada:
    - La tabla muestra todas las sesiones de ese alumno que coinciden
      con los filtros: PC usada, hora de entrada, hora de salida,
      motivo de uso, duración.


  D-2. CERRAR UNA SESIÓN QUE QUEDÓ ABIERTA POR ERROR
  ──────────────────────────────────────────────────────
  Puede pasar si la PC se apagó de golpe y el servidor no detectó la
  desconexión correctamente.

  Opción 1 — Desde Nodos:
    1. Localizar la PC en el mapa (puede aparecer como "activo" aunque
       esté físicamente apagada).
    2. Clic en "Bloquear".
    3. El servidor cierra la sesión con la hora actual como salida.

  Opción 2 — Reiniciar el servidor:
    - Al arrancar, el servidor cierra todas las sesiones que estaban
      marcadas como "activa" y pone todas las terminales en "offline".
    - Útil si hay varias sesiones atascadas a la vez.

  Respuesta esperada:
    - La sesión aparece en el historial con hora de salida.


  D-3. EXPORTAR EL HISTORIAL A EXCEL / PDF
  ──────────────────────────────────────────
  Pasos:
    1. Ir a Historial.
    2. Aplicar los filtros deseados (período, búsqueda, etc.) si los
       necesitás para el PDF.
    3. Clic en "Exportar Excel" o "Exportar PDF".

  Respuesta esperada:
    - EXCEL: siempre exporta TODO el historial completo, sin importar
      los filtros aplicados en pantalla. Esto es correcto — el Excel
      es para tener el registro completo.
    - PDF: exporta SOLO lo que está visible con los filtros aplicados.
      Si no hay filtros, exporta todo lo que aparece en pantalla.

  PENDIENTE (mejora): mejorar el aspecto visual del PDF exportado.


  D-4. POR QUÉ NO APARECE UNA SESIÓN EN EL HISTORIAL
  ──────────────────────────────────────────────────────
  Causas posibles:

    1. Filtro de período incorrecto: el Excel no usa filtros, pero la
       vista del panel sí. Verificar que el período seleccionado
       incluye la fecha de la sesión.

    2. La sesión fue modo offline y la sincronización falló: buscar en
       el "Flujo de Actividad" si hay eventos de esa PC/alumno en esa
       fecha. Si hay eventos pero no sesión, la sincronización offline
       no completó.

    3. La sesión nunca se confirmó (sesión fantasma): el alumno puso el
       DNI pero la PC se desconectó antes de que el kiosco enviara
       "unlock_confirmed". El servidor cancela estas sesiones a los 10s.

    4. Diferencia horaria entre el servidor y las PCs kiosco: puede
       provocar que la sesión quede registrada en una fecha distinta.
       Corregido en v4.37+ (el servidor usa su propia hora para fecha_uso).


───────────────────────────────────────────────────────────────────
  E. ACTIVIDAD Y SOSPECHAS
───────────────────────────────────────────────────────────────────

  E-1. VER QUÉ HIZO UN ALUMNO DURANTE SU SESIÓN
  ────────────────────────────────────────────────
  Pasos:
    1. Ir a pestaña Eventos (Flujo de Actividad).
    2. Escribir el DNI del alumno en el filtro "DNI alumno".
    3. Opcional: filtrar por fecha si querés una sesión específica.

  Respuesta esperada:
    - Lista cronológica de eventos: qué programas abrió, qué descargó.
    - Eventos en rojo = nivel "sospechoso" (cmd, powershell, ejecutables
      descargados, etc.).
    - Eventos en gris = nivel normal (Word, Chrome, documentos).
    - NOTA: los procesos "ignorados" están ocultos por defecto. Para
      verlos todos, clic en "Ver ignorados".


  E-2. INVESTIGAR UNA SOSPECHA
  ──────────────────────────────
  Pasos:
    1. Ir a pestaña Alertas → Sospechas.
    2. Ver la lista de sospechas pendientes.
    3. Clic en "Ver" en la sospecha que querés investigar.
       → Esto abre Eventos con el filtro activado para ese alumno,
         mostrando TODOS los eventos (incluso los ignorados).
    4. Revisar el contexto. Luego volver a Alertas.
    5. Decidir:
       - "Aprobar" → crea una incidencia leve contra el alumno.
       - "Descartar" → la sospecha queda marcada como descartada (no
         crea incidencia).

  Respuesta esperada:
    - Aprobar: la sospecha desaparece de "pendientes", aparece una
      incidencia leve en Alertas → Incidencias para ese alumno.
    - Descartar: la sospecha desaparece de "pendientes", no queda nada
      en incidencias.

  PENDIENTE (mejora): aprobación/descarte por lotes (seleccionar varias
  sospechas y resolver de una sola vez). (Ver sección MEJORAS abajo.)


  E-3. CREAR UNA INCIDENCIA MANUALMENTE
  ────────────────────────────────────────
  Caso de uso: el admin quiere registrar una falta que no fue detectada
  automáticamente (ej: comportamiento inadecuado presencial).

  Pasos:
    1. Ir a Alertas → Incidencias.
    2. Clic en "Nueva incidencia".
    3. Completar: DNI del alumno, tipo (leve / grave), descripción.
    4. Guardar.

  Respuesta esperada:
    - La incidencia aparece en la lista para ese alumno.
    - Sistema de acumulación:
      * 3 incidencias leves activas → aparece alerta de posible baneo
        en la parte superior de la sección.
      * 1 incidencia grave → aparece recomendación de baneo.
      (El baneo NO es automático; el admin lo aplica manualmente en B-2.)

  PENDIENTE (mejora): cuando se crea una incidencia grave, mostrar
  directamente el botón/opción de banear en el mismo lugar (no solo
  arriba). Reevaluar el diseño de respuestas y acciones de incidencias.


  E-4. IGNORAR UN PROCESO DEL SISTEMA (ELIMINAR RUIDO)
  ──────────────────────────────────────────────────────
  Caso de uso: el panel se llena de eventos de un proceso que no es
  relevante (ej: un proceso del sistema o del antivirus).

  Pasos:
    1. Ir a Eventos.
    2. Encontrar un evento de ese proceso (debe ser nivel "normal").
    3. Clic en "Ignorar" en ese evento.

  Respuesta esperada:
    - Ese ejecutable queda en la lista de "ignorados".
    - Ya NO aparece más en la vista limpia de Eventos en NINGUNA PC.
    - PERO: si el nivel del evento era "sospechoso", SIEMPRE se muestra
      (los sospechosos nunca se pueden ignorar — es una protección).
    - El registro en la base de datos NO se borra: sigue guardado para
      evidencia futura.

  LIMITACIÓN CONOCIDA: si un proceso normalmente inofensivo (como Word)
  ejecuta algo en segundo plano que el sistema clasifica como sospechoso,
  ese evento queda marcado en rojo y NO se puede ignorar ni reclasificar
  a "normal". Esto es un comportamiento rígido del sistema actual.
  PENDIENTE: evaluar si se necesita una función para que el superadmin
  pueda reclasificar manualmente un evento de "sospechoso" a "normal".

  Para revertir un proceso ignorado:
    1. En Eventos, clic en "Lista".
    2. Buscar el proceso en la lista de ignorados.
    3. Clic en "Quitar" → vuelve a mostrarse en la vista.

  F. MANTENIMIENTO DEL SISTEMA
───────────────────────────────────────────────────────────────────

  F-1. ACTUALIZAR EL CLIENTE KIOSCO EN TODAS LAS PCS
  ────────────────────────────────────────────────────
  Cómo funciona el sistema de auto-actualización:
    - Cada vez que el kiosco arranca, consulta GET /api/version.
    - El servidor devuelve la versión del archivo C:\WinSysCache\version.txt.
    - El kiosco compara con su versión local (version.local en su carpeta).
    - Si son distintas, descarga el nuevo .exe desde GET /api/descargar-cliente,
      lo guarda, y se reinicia solo.

  Pasos para publicar una nueva versión:
    1. Compilar el cliente:
         dotnet clean
         dotnet publish -c Release -r win-x64 --self-contained true
                        /p:PublishSingleFile=true -o publish\
       (desde la carpeta client/)
    2. Copiar el .exe compilado a C:\WinSysCache\
    3. Editar C:\WinSysCache\version.txt y escribir el nuevo número
       (ej: "4.38"). Solo el número, sin "v" ni espacios extra.
    4. Reiniciar el servidor (para que lea el nuevo version.txt).

  Respuesta esperada al reiniciar cada kiosco:
    - El kiosco detecta que la versión del servidor es mayor a la local.
    - Descarga el nuevo .exe automáticamente.
    - Se reinicia y muestra la nueva versión en la pantalla de login.
    - NOTA: si el kiosco ya estaba corriendo y no se reinicia, la
      actualización ocurre en el próximo reinicio.

  Si un kiosco no se actualiza:
    - Verificar que el servidor esté corriendo y accesible desde esa PC.
    - Revisar que version.txt tenga el número correcto (sin espacios).
    - El kiosco escribe en su log (App.log en su carpeta) si falla.


  F-2. HACER UN BACKUP DE LA BASE DE DATOS
  ──────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN.

  Pasos:
    1. Ir a Configuración (pestaña en el panel).
    2. Buscar la sección de Backup SQL.
    3. Clic en "Descargar backup".

  Respuesta esperada CORRECTA:
    - El servidor ejecuta mysqldump sobre toda la base de datos.
    - Se descarga un archivo .sql con TODA la base: estructura de tablas
      Y todos los datos (alumnos, sesiones, historial, actividad, etc.).
    - Al restaurarlo en otro servidor se recupera todo el estado.

  BUG CONOCIDO: actualmente el backup solo guarda la estructura de las
  tablas (CREATE TABLE) pero NO los datos (INSERT INTO). Esto hace que
  el backup no sirva para restaurar registros.
  PENDIENTE (crítico): corregir el backup para que incluya los datos.
  (Ver sección MEJORAS abajo.)

  Si falla la descarga:
    - El servidor no encuentra mysqldump en el PATH de Windows.
    - Solución: asegurar que mysqldump.exe esté en el PATH, o configurar
      su ruta en server/.env


  F-3. QUÉ HACER SI EL SERVIDOR NO ARRANCA
  ──────────────────────────────────────────
  Síntomas: el panel no carga (pantalla en blanco o error de conexión),
  los kioscos se quedan conectando indefinidamente.

  Pasos de diagnóstico:
    1. Ir a la PC del servidor. Abrir la terminal donde corre el servidor.
       El error aparece en los últimos mensajes impresos.
    2. Causas comunes y solución:
       - "Can't connect to MySQL": MySQL/XAMPP no está corriendo.
         Abrir XAMPP y arrancar el servicio MySQL.
       - "Address already in use" (puerto 8000 ocupado):
         Cerrar el proceso anterior o usar otro puerto.
       - "No module named X": falta una dependencia.
         Correr: cd server && .venv\Scripts\activate && pip install -r requirements.txt
       - Credenciales incorrectas en .env: verificar server/.env
    3. Arrancar de nuevo:
         cd server
         .venv\Scripts\activate
         uvicorn main:app --host 0.0.0.0 --port 8000

  Respuesta esperada al reiniciar exitosamente:
    - El servidor imprime: "Application startup complete."
    - AUTOMÁTICAMENTE cierra todas las sesiones que estaban abiertas
      y pone todas las terminales en "offline".
    - Los kioscos reconectan solos (tienen reconexión automática cada
      pocos segundos).

  PARA PROBARLO: simplemente detener el servidor (Ctrl+C en la terminal)
  y volver a arrancarlo. Ver que los kioscos vuelven a conectarse solos
  y las sesiones abiertas quedan cerradas en el historial.


  F-4. CÓMO AGREGAR UNA TERMINAL NUEVA
  ──────────────────────────────────────
  (PC nueva donde instalar el kiosco)

  Pasos:
    1. Copiar el archivo ControlBiblioteca.Client.exe a la PC nueva.
       (desde C:\WinSysCache\ del servidor)
    2. Crear en la misma carpeta el archivo kiosco.config.json con este
       contenido EXACTO (las claves son ServerIp y ServerPort, separadas;
       NO es una sola URL):
         {
           "ServerIp": "<IP_DEL_SERVIDOR>",
           "ServerPort": 8000
         }
       Reemplazar <IP_DEL_SERVIDOR> con la IP real de la PC del servidor
       (ej: "192.168.1.33"). ServerPort va SIN comillas (es un número).
       Si el archivo falta o está mal, el kiosco usa 127.0.0.1:8000 por defecto
       (es decir, no encontrará al servidor en otra PC).
    3. Ejecutar el .exe como Administrador.

  Respuesta esperada:
    - El kiosco se conecta al servidor.
    - En el panel (Nodos), aparece una tarjeta nueva con el nombre de
      esa PC y estado "bloqueado".
    - La terminal se registra automáticamente en la base de datos.
    - El nombre que aparece es el HOSTNAME de Windows de esa PC.

  H. MENSAJES PROGRAMADOS AL KIOSCO  [NUEVO]
............................................................................

  Hay dos tipos de mensajes que el servidor puede enviar a todas las PCs
  kiosco en una hora determinada:
    - "cierre"  → se repite cada día a la misma hora (ej: aviso de cierre
                  a las 21:45). El sistema lo marca como "enviado hoy" y
                  lo vuelve a enviar el día siguiente.
    - "extra"   → se envía una sola vez en la fecha/hora indicada y queda
                  marcado como enviado para no repetirse.

  El kiosco muestra el mensaje como un TOAST (aviso superpuesto en pantalla)
  durante 5 segundos, sin interrumpir la sesión activa.

  H-1. PROGRAMAR UN MENSAJE DE CIERRE DIARIO
  ─────────────────────────────────────────────
  Caso de uso: avisar a todos los alumnos "La sala cerrará en 15 minutos"
  todos los días a las 21:45.

  Quién puede hacerlo: SOLO SUPERADMIN.

  Pasos:
    1. Ir a Configuración → Actividad del Sistema (sub-pestaña).
    2. Buscar la sección "Mensajes programados".
    3. Elegir tipo: "Cierre diario".
    4. Escribir el mensaje (ej: "La sala cerrará en 15 minutos.").
    5. Elegir la hora de envío (formato HH:MM).
    6. Guardar.

  Respuesta esperada:
    - Cada día a esa hora, el servidor envía el mensaje a TODAS las PCs
      conectadas en ese momento.
    - Las PCs apagadas o sin conexión en ese instante NO reciben el
      mensaje (no se reenvía cuando reconectan).
    - En la consola del servidor aparece:
        [MSG] Mensaje de cierre enviado: "La sala cerrará..."

  PARA PROBARLO:
    1. Crear un mensaje de cierre con la hora actual + 1 minuto.
    2. Esperar. Verificar que el toast aparece en los kioscos conectados.


  H-2. PROGRAMAR UN MENSAJE EXTRA (ÚNICO)
  ────────────────────────────────────────
  Caso de uso: avisar sobre un evento puntual ("Hoy no hay clases en el
  piso 2") que solo debe salir una vez.

  Pasos:
    1. Igual que H-1, pero elegir tipo: "Mensaje extra".
    2. Escribir el mensaje.
    3. Elegir hora de envío.
    4. Guardar.

  Respuesta esperada:
    - El mensaje se envía una única vez cuando llega la hora.
    - Después queda marcado como "enviado" y no vuelve a enviarse aunque
      la hora coincida al día siguiente.

  PARA PROBARLO:
    1. Crear un mensaje extra con la hora actual + 1 minuto.
    2. Verificar que aparece en los kioscos.
    3. Esperar otro minuto y verificar que NO se repite.


  H-3. QUÉ VE EL ALUMNO CUANDO LLEGA EL MENSAJE
  ────────────────────────────────────────────────
  - Aparece un TOAST (banda de aviso) superpuesto en la pantalla del
    kiosco, con el texto del mensaje, durante 5 segundos.
  - Si el alumno está en plena sesión, el aviso no la interrumpe: el
    toast desaparece solo y el alumno puede seguir trabajando.
  - Si la PC está bloqueada (pantalla de login), el aviso también
    aparece.

  I. MODO OFFLINE DEL KIOSCO  [NUEVO]
............................................................................

  I-1. QUÉ ES EL MODO OFFLINE Y CUÁNDO SE ACTIVA
  ─────────────────────────────────────────────────
  El modo offline permite que un alumno use una PC aunque el servidor no
  sea alcanzable por red. Lo activa el ENCARGADO (no el alumno solo),
  mediante un atajo de teclado secreto + PIN.

  Se activa SOLO cuando el kiosco está en estado desconectado:
    - El contador de reconexión está corriendo (pantalla de desconexión).
    - Si hay conexión activa, el atajo no funciona.

  Datos registrados offline:
    - DNI del alumno, razón de uso, hora de inicio, terminal (hostname).
    - Todo queda en offline_sessions.json en la carpeta del kiosco.
    - Cuando la red vuelve, el servidor intenta sincronizar la sesión.

  NOTA: el modo offline es de emergencia, no el flujo habitual. Requiere
  que el encargado esté físicamente presente en la PC.


  I-2. CÓMO USAR EL MODO OFFLINE (FLUJO COMPLETO)
  ──────────────────────────────────────────────────
  Escenario: el servidor está caído o la red no llega. Un alumno necesita
  usar la PC y el encargado decide habilitarla manualmente.

  Pasos:
    1. Verificar que el kiosco muestra la pantalla de desconexión
       (contador de reconexión corriendo). Si hay conexión, el atajo
       no funciona.
    2. El alumno escribe su DNI y razón de uso en el formulario
       principal del kiosco (los campos ya visibles en la pantalla).
    3. El encargado presiona el atajo de teclado offline (por defecto:
       Ctrl+Alt+F11, configurable desde el panel — ver I-4 / J-3).
    4. Aparece una ventana: "Acceso Offline — Encargado".
       El encargado escribe su PIN offline y presiona "Continuar".
       - Si el PIN es incorrecto, el campo se limpia y se puede reintentar.
       - Escapar (ESC) cancela sin dejar rastro.
    5. Si el PIN es correcto:
       - El kiosco se desbloquea con el DNI y razón ya escritos.
       - Muestra "Bienvenido, [DNI]" (sin nombre porque no hay servidor).
       - La sesión queda activa de forma indefinida hasta que el alumno
         termine o el encargado bloquee manualmente.
    6. Cuando el alumno termina: el encargado cierra la sesión normalmente
       (o la PC se bloquea al perder alimentación).

  Si el DNI NO se escribió antes de presionar el atajo:
    - Aparece un diálogo adicional donde el encargado escribe el DNI y
      la razón directamente (flujo de respaldo).

  Respuesta esperada en el log (autoupdate.log o App.log de la PC):
    [Offline] Hotkey registrado (Mod:X Key:Y)
    [Offline] Sesión iniciada — DNI:12345678 Razón:tarea

  PARA PROBARLO:
    1. Desconectar la PC del servidor (apagar el servidor o desenchufar
       el cable de red).
    2. Esperar que el kiosco muestre la pantalla de desconexión.
    3. Escribir un DNI y razón.
    4. Presionar Ctrl+Alt+F11.
    5. Ingresar el PIN (por defecto: ver kiosco.config.json campo
       "OfflinePin", o el que se haya configurado en el panel).
    6. Verificar que el kiosco se desbloquea.


  I-3. QUÉ PASA CUANDO LA RED VUELVE (SINCRONIZACIÓN)
  ──────────────────────────────────────────────────────
  Cuando el kiosco detecta que el servidor volvió a ser alcanzable
  mientras hay una sesión offline activa:

  a) El kiosco muestra el toast: "Conexión restaurada. Verificando
     datos del alumno..."

  b) El servidor verifica el DNI:
     - Existe en el maestro de alumnos.
     - No tiene un ban activo.

  c) Resultado "ok":
     - El kiosco muestra: "Conexión restaurada. Sesión sincronizada."
     - La sesión offline pasa a ser una sesión normal y se registra
       en el historial del servidor.
     - El alumno puede seguir trabajando sin interrupción.

  d) Resultado "baneado" o "no registrado":
     - Aparece un contador de 3 minutos visible con el motivo
       (ej: "DNI baneado. La sesión se cerrará en X segundos.").
     - Al terminar el contador, la PC se bloquea automáticamente.
     - El encargado debe atender al alumno.

  Registro local:
    - En offline_sessions.json queda la entrada con estado:
        "sync:ok"        → sincronización exitosa
        "sync:baneado"   → alumno estaba baneado
        "sync:no_existe" → DNI no encontrado en el servidor


  I-4. LOG LOCAL DE SESIONES OFFLINE
  ─────────────────────────────────────
  Cada sesión offline genera una entrada en el archivo:
    offline_sessions.json
  (en la misma carpeta donde está el .exe del kiosco)

  Cada entrada incluye:
    { "dni": "...", "razon": "...", "hora_inicio": "...",
      "hora_fin": "...", "estado": "...", "terminal": "PC-01" }

  Estados posibles:
    "activa"         → sesión en curso (la PC no se cerró limpiamente)
    "cerrada_manual" → el encargado cerró la sesión manualmente
    "sync:ok"        → se sincronizó con el servidor al reconectar
    "sync:baneado"   → el DNI tenía ban, sesión terminada por el sistema
    "sync:no_existe" → DNI no reconocido por el servidor

  El archivo es de solo-append. Si el kiosco se apaga durante una sesión
  offline activa, la entrada queda con estado "activa" (sin hora_fin).

  J. ATAJO DE MANTENIMIENTO (SALIDA DE EMERGENCIA)  [NUEVO]
............................................................................

  J-1. PARA QUÉ SIRVE
  ─────────────────────
  El atajo de mantenimiento permite que el encargado cierre el kiosco
  de emergencia y regrese al escritorio de Windows, sin necesidad de
  contraseña de Windows ni de cerrar sesión del servidor.

  Casos de uso típicos:
    - La PC kiosco colgó y hay que reiniciarla.
    - Se necesita instalar una actualización manual.
    - El kiosco tiene un problema que requiere acceso al escritorio.

  ACLARACIÓN IMPORTANTE: esta salida cierra el kiosco completamente
  (EscaparAExplorer). NO es lo mismo que bloquear al alumno: la PC
  vuelve al escritorio de Windows, no a la pantalla de login del kiosco.
  Volver al kiosco requiere volver a ejecutar el .exe.


  J-2. CÓMO USARLO (DOS MÉTODOS)
  ─────────────────────────────────

  MÉTODO 1 — Atajo rápido (Ctrl+Alt+F10, configurable):
    1. Presionar la combinación configurada (por defecto: Ctrl+Alt+F10).
    2. El kiosco se cierra inmediatamente y regresa al escritorio.
    - NO pide confirmación ni PIN. Es instantáneo.
    - Funciona tanto si el kiosco está bloqueado como si hay sesión activa.
    - Si había sesión activa, el servidor la detecta como desconexión
      y cierra la sesión con motivo "desconexion_red".

  MÉTODO 2 — Secuencia Ctrl+M + 5x ESC (método legado/alternativo):
    1. Presionar Ctrl+M. El kiosco activa el modo de escape internamente
       (no hay aviso visual — solo se registra en el log interno).
    2. Dentro de los 5 segundos siguientes, presionar ESC exactamente 5 veces.
    3. El kiosco se cierra y regresa al escritorio.
    - Si pasan más de 5 segundos sin completar los 5 ESC, el contador
      se resetea y hay que empezar desde Ctrl+M otra vez.
    - No pide PIN.

  PARA PROBARLO (método 1):
    1. Con el kiosco corriendo (bloqueado o con sesión), presionar
       Ctrl+Alt+F10.
    2. Verificar que el kiosco se cierra y el escritorio de Windows
       queda visible.
    3. En el log del servidor debería aparecer la terminal como "offline".


  J-3. CONFIGURAR EL PIN Y LA TECLA DESDE EL PANEL
  ───────────────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN.

  El atajo y PIN del modo offline (Ctrl+Alt+F11 por defecto) y el atajo
  de mantenimiento (Ctrl+Alt+F10) se pueden cambiar desde el panel sin
  tener que editar archivos en cada PC: el servidor los distribuye
  automáticamente a todos los kioscos conectados.

  Pasos:
    1. Ir a Configuración → sub-pestaña "Backdoor" (solo visible para
       superadmin).
    2. Ajustar:
         - "Atajo de mantenimiento": la combinación de teclas.
         - "PIN de mantenimiento": mínimo 4 caracteres.
    3. Guardar.
    4. El servidor envía la nueva configuración a TODOS los kioscos
       conectados en ese momento via WebSocket (tipo: config_backdoor_update).
       Los kioscos desconectados la recibirán al reconectar.

  Para el modo offline (Ctrl+Alt+F11), el flujo es el mismo pero en la
  sub-pestaña "Offline" del mismo panel.

  NOTA: si el kiosco no está conectado cuando se cambia la config, la
  nueva configuración llega al reconectarse. Hasta ese momento usa el
  PIN y atajo anteriores.

  PARA PROBARLO:
    1. Cambiar el PIN de mantenimiento desde el panel.
    2. En un kiosco conectado, verificar que el nuevo PIN funciona
       inmediatamente (sin reiniciar).
    3. Desconectar un kiosco, cambiar el PIN otra vez, reconectar el
       kiosco y verificar que adopta el nuevo PIN.

  K. INDICADORES / KPIs DEL PANEL  [NUEVO]
............................................................................

  Sección del panel admin que muestra métricas del sistema (equipos,
  alumnos, seguridad) calculadas en vivo desde la base de datos. Es una
  vista nueva en el menú lateral, llamada "Indicadores".

  El tablero es ÚNICO para todo el panel (no por usuario): lo que se
  muestra y en qué orden lo decide el superadmin, y todos lo ven igual.


  K-1. VER LOS INDICADORES
  ─────────────────────────────
  Quién puede hacerlo: admin y superadmin.

  Pasos:
    1. En el menú lateral, clic en "Indicadores".
    2. Aparecen las tarjetas KPI activas, cada una con: categoría,
       valor grande, y la etiqueta de lo que mide.
    3. Botón "Refrescar" para recalcular los valores al instante.

  Respuesta esperada:
    - Los valores se calculan en el momento desde la base de datos
      (no son históricos congelados).
    - Formatos: número entero, porcentaje (ej. ocupación), o duración
      (ej. "1h 25m" para promedios de tiempo).

  NOTA: los valores reflejan el estado al momento de abrir la vista o de
  tocar "Refrescar". No se actualizan solos segundo a segundo.


  K-2. PERSONALIZAR EL TABLERO (SOLO SUPERADMIN)
  ──────────────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN. El admin solo ve el resultado;
  no le aparece el botón "Personalizar".

  Pasos:
    1. Ir a "Indicadores".
    2. Clic en "Personalizar" (arriba a la derecha; solo visible para
       superadmin).
    3. Se abre una lista con TODOS los indicadores disponibles:
       - Marcar/desmarcar la casilla = mostrar/ocultar ese KPI.
       - Arrastrar una fila (icono de puntos) = reordenar.
    4. Clic en "Guardar".

  Respuesta esperada:
    - El tablero se actualiza con los KPIs marcados, en el orden elegido.
    - La configuración queda guardada para TODO el panel (todos los
      usuarios la verán al recargar).
    - La acción queda registrada en Auditoría
      (acción "cambiar_config_kpis").

  Si un admin intenta guardar (por API directa):
    - El servidor responde 403 (solo superadmin puede modificar).

  PARA PROBARLO:
    1. Como superadmin, abrir "Personalizar", activar 2-3 KPIs nuevos,

    2. Recargar la página (F5): el tablero conserva la configuración.

  K-4. QUIÉN VE QUÉ (ROLES)

  M. BANCO DE PROGRAMAS Y BANCO DE RUIDO (EVENTOS)  [NUEVO]
............................................................................

  Dentro de la pestaña "Eventos" (Actividad) hay tres sub-pestañas:
    - Flujo        → el registro de actividad de siempre.
    - Banco de apps → lista blanca de programas reconocidos.
    - Banco de ruido → procesos de fondo que no son actividad del alumno.


  M-1. PARA QUÉ SIRVE (EL PROBLEMA QUE RESUELVE)
  ─────────────────────────────────────────────────
  El cliente del kiosco registra TODO lo que se ejecuta en la PC, no solo
  lo que abre la persona. Windows, por su cuenta, lanza cientos de procesos
  internos (svchost, DeviceCensus, Windows Update, antivirus, etc.). Sin
  filtro, esos procesos ahogarían la pantalla y harían inútil cualquier
  intento de ver "qué usan realmente los estudiantes".

  El banco invierte la lógica a una LISTA BLANCA (fail-closed):
    "Lo que NO está reconocido se marca como SOSPECHOSO hasta que el
     superadmin lo clasifique."

  Así, en lugar de perseguir una lista negra interminable, el superadmin
  va construyendo un catálogo de lo aceptable, y el sistema resalta
  automáticamente lo que no conoce.


  M-2. LOS TRES ESTADOS DE UN PROGRAMA
  ────────────────────────────────────────
  Cada ejecutable (.exe) visto en actividad cae en uno de tres estados:

    1. EN EL BANCO DE APPS  → es una app real del alumno (Word, Chrome,
       AutoCAD…). Se registra como evento NORMAL.
    2. EN EL BANCO DE RUIDO → es un proceso de fondo (actualizadores,
       servicios de Windows…). Se registra NORMAL pero se OCULTA del Flujo.
    3. EN NINGUNO           → SOSPECHOSO. Genera una entrada de sospecha y
       aparece resaltado, hasta que el superadmin lo clasifique.

  IMPORTANTE — herramientas peligrosas: cmd, powershell, regedit, psexec,
  etc. NUNCA se ponen en ningún banco a propósito. El cliente ya las marca
  como sospechosas y el banco NO rebaja esa marca. Aunque alguien las
  agregara por error, el sistema respeta la sospecha del cliente.

  El banco viene PRE-CARGADO de fábrica con ~50 apps comunes y ~150
  procesos de ruido de Windows ya identificados (con su descripción),
  para que el panel arranque casi limpio. El superadmin puede ajustar
  todo a mano.


  M-3. CLASIFICAR UN PENDIENTE (ES PROGRAMA / ES RUIDO)
  ─────────────────────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN.

  En "Banco de apps", arriba hay una zona "Pendientes por clasificar":
  todo .exe visto en actividad que aún no está en ningún banco, ordenado
  por cuántos alumnos distintos lo usaron. Cada pendiente trae una
  SUGERENCIA del sistema ("Parece app" / "Parece ruido" / "Desconocido")
  y, si lo reconoce, su nombre y descripción.

  Pasos:
    1. Revisar el pendiente. Ver cuántos alumnos lo usaron (icono de
       personas) y cuántas veces (icono de ojo).
    2. Clic en "Es programa" (lo manda al banco de apps) o "Es ruido"
       (lo manda al banco de ruido).
    3. Se abre el formulario pre-rellenado con la sugerencia. Confirmar
       nombre/categoría (apps) o el dueño (ruido) y Guardar.

  EFECTO RETROACTIVO (importante): al clasificar, el sistema CORRIGE el
  pasado. Todos los eventos viejos de ese .exe que estaban como
  sospechosos pasan a normal, y sus sospechas pendientes se cierran
  (se marcan "descartadas" con tu usuario). El historial queda coherente
  con el banco actual. Al guardar, el mensaje indica cuántos eventos se
  corrigieron.


  M-4. AGREGAR O QUITAR MANUALMENTE DEL BANCO
  ───────────────────────────────────────────────
  Quién puede hacerlo: SOLO SUPERADMIN.

  Agregar sin esperar a que aparezca como pendiente:
    1. En "Banco de apps" o "Banco de ruido", clic en "Agregar programa" /
       "Agregar ruido".
    2. Escribir el ejecutable (ej. winword.exe), su nombre y descripción.
    3. Guardar (también es retroactivo).

  Quitar:
    1. En la tabla del banco, clic en la papelera de la fila.
    2. Confirmar. ATENCIÓN: al quitarlo, ese programa VOLVERÁ a aparecer
       como sospechoso la próxima vez que alguien lo ejecute (vuelve al
       estado 3).


  M-5. EL BANCO DE RUIDO Y "PERTENECE A"
  ──────────────────────────────────────────
  El ruido no es anónimo: cada proceso de ruido tiene un DUEÑO, que indica
  de qué viene. Puede ser:
    - "Windows / Sistema"  → ruido del propio sistema operativo
      (svchost, Windows Update, antivirus…).
    - Un programa del banco → ej. GoogleUpdate.exe pertenece a Google
      Chrome; los procesos de Office pertenecen a Word.

  La columna "Pertenece a" de la tabla muestra ese dueño en lenguaje
  claro. Al clasificar algo como ruido, se elige el dueño de un
  desplegable (Windows/Sistema o cualquier app ya en el banco).


  M-6. QUÉ CAMBIA EN EL FLUJO DE ACTIVIDAD
  ─────────────────────────────────────────────
  - El Flujo (vista limpia) OCULTA tanto los "procesos ignorados" (E-4)
    como todo lo que esté en el banco de ruido. Solo verás apps reales y
    sospechas.
  - Los eventos sospechosos SIEMPRE se ven, aunque su .exe esté listado
    (para no esconder algo que el cliente marcó como peligroso).
  - El botón "Ver ignorados / Viendo todo" sigue funcionando: al
    investigar, muestra absolutamente todo, ruido incluido.


  M-7. QUIÉN PUEDE ACCEDER (ROLES)
  ────────────────────────────────────
  - VER los bancos y los pendientes: admin y superadmin.
  - CLASIFICAR, agregar o quitar: SOLO SUPERADMIN. Si un admin intenta
    editar, el servidor responde 403 (fail-closed). Los botones de edición
    ni siquiera se le muestran.
  - Toda clasificación/alta/baja queda registrada en Auditoría.


  M-8. VULNERABILIDADES Y LÍMITES CONOCIDOS
  ───────────────────────────────────────────────
  Detectados durante la implementación; conviene tenerlos presentes:

    1. EJECUTABLES VERSIONADOS EN EL NOMBRE. Algunos procesos incluyen su
       versión en el nombre (ej. am_delta_patch_1.451.249.0.exe,
       microsoftedge_x64_149.0.4022.69_….exe). Cada versión es un nombre
       distinto, así que no se pueden listar de antemano y volverán a
       caer como pendientes/sospechosos cada vez que cambie la versión.
       Es ruido real, pero de bajo volumen. Mejora futura: reconocer por
       prefijo/patrón, no por nombre exacto.

    2. LA DECISIÓN ES POR NOMBRE DE .EXE, NO POR FIRMA. Si alguien
       renombra una herramienta peligrosa con el nombre de una app del
       banco (ej. renombrar cmd.exe a "winword.exe"), pasaría como
       reconocida. Mitigación actual: la marca de "sospechoso" del cliente
       (herramientas peligrosas) se respeta SIEMPRE y el banco no la
       rebaja; pero un binario arbitrario renombrado sí podría colarse.
       Mejora futura: validar ruta/firma del ejecutable.

    3. EL CIERRE RETROACTIVO DE SOSPECHAS ES POR TEXTO. Al clasificar, las
       sospechas viejas se cierran buscando el nombre del .exe dentro del
       detalle de la sospecha. Es robusto en la práctica (el detalle
       incluye el ejecutable), pero si una sospecha fue creada con otro
       texto, podría no cerrarse automáticamente. Los eventos de actividad
       sí se corrigen siempre (esos sí guardan proceso_exe exacto).

    4. PRE-CARGA SOLO SI EL BANCO ESTÁ VACÍO. El sembrado de fábrica corre
       una única vez (cuando las tablas están vacías). Si en el futuro se
       amplía el catálogo de fábrica, los servidores ya inicializados NO
       reciben las nuevas entradas automáticamente; habría que re-sembrar
       o agregarlas a mano.

    5. CACHÉ EN MEMORIA. Para no consultar la BD en cada evento, los bancos
       se cachean en memoria y se refrescan al editar desde el panel. Si se
       modifican las tablas DIRECTAMENTE en MySQL (sin pasar por el panel),
       hay que reiniciar el servidor para que tome los cambios.

  N. VIGENCIA DE CREDENCIALES (CARNET DE BIBLIOTECA)  [NUEVO]
═══════════════════════════════════════════════════════════════════

  N-1. PARA QUÉ SIRVE
  ─────────────────────────────────────────────────
  El carnet de biblioteca de cada estudiante tiene una fecha de
  caducidad. Vencido ese plazo, el alumno no debe poder usar las PCs
  hasta renovarlo. El sistema aplica ese corte automáticamente.

  Cada estudiante tiene tres fechas en el padrón:

    fecha_alta        Cuándo entró al padrón (registro del carnet).
    fecha_caducidad   Vencimiento REAL del carnet. Es la que manda.
    fecha_renovacion  Cuándo se renovó desde el panel. Casi siempre
                      vacía: la mayoría saca carnet nuevo en vez de
                      renovar.

  Cómo se decide si está vencido:
    1. Si tiene fecha_caducidad  → se compara contra hoy.
    2. Si NO la tiene            → se calcula fecha_alta + vigencia
                                   (24 meses por defecto).
    3. Si no tiene ninguna fecha → sin vencimiento (padrón base).

  La vigencia en meses es configurable: tabla ajustes_sistema, clave
  'vigencia_meses'. Si no existe, se usan 24 meses.


  N-2. QUÉ PASA CUANDO UN ALUMNO CON CARNET VENCIDO INTENTA ENTRAR
  ─────────────────────────────────────────────────
  El bloqueo es del lado del SERVIDOR, en los dos caminos posibles:

  a) El alumno escribe su DNI en la PC:
     El servidor rechaza el login y el kiosco muestra:
       "Su carnet venció el DD/MM/AAAA. Debe renovarlo en biblioteca
        para usar las PCs."
     La PC sigue bloqueada. No se crea sesión.

  b) El encargado intenta desbloquear la PC desde el panel:
     El panel muestra el error:
       "Carnet VENCIDO el DD/MM/AAAA. [Nombre] debe renovar su carnet
        en biblioteca para poder usar las PCs."
     No se envía la orden de desbloqueo.

  Como el corte vive en el servidor, no hace falta actualizar ni
  recompilar el cliente de las PCs.


  N-3. VER QUIÉNES ESTÁN VENCIDOS
  ─────────────────────────────────────────────────
  1. Panel → Base de Datos → Estudiantes.
  2. Cada fila muestra una columna "Vigencia":
       Verde  "Vence DD/MM/AAAA"  → vigente
       Rojo   "Vencida"           → no puede usar las PCs
       "—"                        → sin vencimiento (padrón base)
  3. Las filas vencidas quedan resaltadas en rojo tenue.
  4. Botón "Solo vencidas": filtra el listado para ver únicamente
     las credenciales caducadas.

  También hay un indicador global:
     Panel → Indicadores → Usuarios → "Credenciales vencidas".


  N-4. RENOVAR LA CREDENCIAL DE UN ALUMNO
  ─────────────────────────────────────────────────
  1. Panel → Base de Datos → Estudiantes.
  2. Buscar al alumno (o activar "Solo vencidas").
  3. En la fila vencida aparece un botón de renovar (icono de
     recarga). Solo aparece si la credencial está vencida.
  4. Confirmar en el aviso.
  5. El sistema:
       - Extiende fecha_caducidad a hoy + vigencia (24 meses).
       - Registra fecha_renovacion = hoy.
       - NO toca fecha_alta (el registro original es histórico).
       - Deja constancia en Auditoría.
  6. El alumno ya puede volver a usar las PCs de inmediato.

  Quién puede hacerlo: admin y superadmin.


  N-5. DE DÓNDE SALEN LAS FECHAS REALES
  ─────────────────────────────────────────────────
  Las fechas de registro y caducidad provienen del sistema de
  biblioteca (Koha), que exporta un CSV con estas columnas:

    cardnumber        DNI del alumno (su carnet usa el DNI)
    categorycode      ST = estudiante (lo demás se descarta)
    FECHA_REGISTRO    fecha de alta real
    FECHA_CADUCIDAD   vencimiento real del carnet
    FECHA_RENOVACIÓN  solo en los pocos casos renovados

  ADVERTENCIA: el "Importar Excel" del panel NO carga fechas de
  vigencia (el Excel del padrón no las tiene). Si se importa solo por
  ahí, todos los alumnos quedan sin caducidad y el sistema les calcula
  fecha_alta + 24 meses, lo que da vencimientos irreales.
  Para cargar las fechas verdaderas hay que cruzar el padrón con el
  CSV de Koha.


  N-6. EXPORTAR EL PADRÓN CON LAS FECHAS
  ─────────────────────────────────────────────────
  Panel → Base de Datos → Estudiantes → "Exportar Excel".
  El archivo incluye, además de los datos del alumno:

    Fecha de ingreso     (fecha_alta)
    Fecha de vigencia    (caducidad real, o la calculada)
    Fecha de renovación  (vacía si nunca se renovó)

  Solo superadmin puede exportar.

  O. MOTIVOS DE USO GESTIONABLES  [NUEVO]
═══════════════════════════════════════════════════════════════════

  O-1. QUÉ SON
  ─────────────────────────────────────────────────
  Son las razones que el alumno elige en la PC al iniciar sesión
  ("Investigación", "Tarea", "Clases virtuales"…). Antes eran fijas;
  ahora se administran desde el panel.

  El cliente del kiosco pide la lista al servidor cada vez que
  arranca, así que los cambios llegan a las PCs SIN recompilar ni
  reinstalar nada: basta con reiniciar el cliente.

  Dónde: Panel → Configuración → Motivos de uso.
  Quién: admin y superadmin.


  O-2. AGREGAR UN MOTIVO
  ─────────────────────────────────────────────────
  1. Panel → Configuración → Motivos de uso.
  2. Escribir el texto en el campo de arriba.
  3. Clic en "Agregar".
  4. Aparece en la lista de activos.
  5. Las PCs lo mostrarán al reiniciar el cliente.

  El sistema rechaza motivos vacíos, de más de 200 caracteres o
  repetidos (avisa: "Ya existe el motivo «…»").


  O-3. EDITAR UN MOTIVO
  ─────────────────────────────────────────────────
  1. Clic en el icono de lápiz del motivo.
  2. Corregir el texto y aceptar.
  3. Se guarda y queda registrado en Auditoría.

  Nota: las sesiones ya registradas conservan el texto que tenían al
  momento de crearse.


  O-4. QUITAR UN MOTIVO (DESACTIVAR)
  ─────────────────────────────────────────────────
  Los motivos NUNCA se borran de verdad: se desactivan. Así el
  historial de sesiones que ya los usó no se rompe.

  1. Clic en el icono de ojo tachado.
  2. El sistema avisa cuántas sesiones lo usaron, por ejemplo:
       "Se usó en 80 sesión(es). El historial las conserva; solo deja
        de aparecer en las PCs."
  3. Confirmar.
  4. El motivo pasa a la lista "Desactivados" (atenuado y tachado) y
     desaparece de las PCs.


  O-5. VOLVER A ACTIVAR UN MOTIVO
  ─────────────────────────────────────────────────
  1. Buscarlo en la sección "Desactivados" al final de la lista.
  2. Clic en el icono de recarga.
  3. Vuelve a la lista de activos y reaparece en las PCs.


  O-6. CUIDADO: NO DEJAR LA LISTA VACÍA
  ─────────────────────────────────────────────────
  Si se desactivan TODOS los motivos, el alumno no tendría ninguna
  opción que elegir al iniciar sesión. El panel advierte con el
  mensaje "Ningún motivo activo: el alumno no vería opciones".
  Mantener siempre al menos uno activo.
