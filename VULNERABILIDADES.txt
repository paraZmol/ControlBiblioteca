ANÁLISIS DE VULNERABILIDADES — Control Biblioteca UNASAM
Actualizado: 2026-06-02
=========================================================

Clasificación por urgencia:
  [NECESARIO]  → Riesgo real e inmediato. Resolver antes de producción.
  [MEDIO]      → Riesgo moderado. Resolver en la siguiente iteración.
  [BAJO]       → Riesgo menor o mitigado por contexto. Resolver cuando sea posible.


═══════════════════════════════════════════════════════════
  CATEGORÍA A — NECESARIO (resolver antes de producción)
═══════════════════════════════════════════════════════════

──────────────────────────────────────────────────────────
A-1. [NECESARIO] WebSocket /ws/admin sin autenticación
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — endpoint /ws/admin

Descripción:
  Cualquier dispositivo en la misma red puede conectarse al WebSocket
  de administración sin usuario ni contraseña.

Prueba confirmada (14/05/2026):
  const ws = new WebSocket('ws://localhost:8000/ws/admin');
  Resultado: conectado sin login. Recibe estado de terminales en tiempo real.

Impacto:
  - Ver estado, IPs y nombres de alumnos usando las PCs
  - Posiblemente bloquear/desbloquear terminales sin autenticación
  - Alcanzable desde el WiFi del laboratorio por cualquier alumno con celular

Cómo arreglarlo:
  - Validar JWT token al conectarse al WebSocket
  - Si no hay token válido → cerrar conexión inmediatamente
  NOTA: Ya existe la validación en el código (mayo 2026), verificar que esté activa.


──────────────────────────────────────────────────────────
A-2. [NECESARIO] SECRET_KEY de JWT débil o ausente en producción
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/auth_service.py

Descripción:
  SECRET_KEY usa fallback si no está en .env:
    SECRET_KEY = os.getenv("SECRET_KEY", "clave-secreta-cambiar-en-produccion")
  Con la clave por defecto cualquiera puede firmar tokens JWT válidos.

Impacto:
  - Forjar tokens de superadmin sin conocer contraseña
  - Acceso total al sistema

Cómo arreglarlo:
  - Eliminar el fallback y lanzar RuntimeError si no está configurada
  - Generar clave segura: openssl rand -hex 32
  - Guardarla en .env (nunca en el código)


──────────────────────────────────────────────────────────
A-3. [NECESARIO] Verificación SSL deshabilitada en llamada a API externa
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — línea ~104

Descripción:
  La consulta al SGA UNASAM usa verify=False:
    async with httpx.AsyncClient(timeout=_SGA_TIMEOUT, verify=False)
  Permite ataques MITM que intercepten y alteren datos de alumnos.

Impacto:
  - Un atacante en la red puede suplantar la API del SGA
  - Inyectar datos de alumnos falsos

Cómo arreglarlo:
  - Instalar el certificado del SGA correctamente
  - Usar verify=True o pasar el path del certificado: verify="/ruta/cert.pem"


──────────────────────────────────────────────────────────
A-4. [NECESARIO] SQL dinámico con parámetros sin sanitizar en estadísticas
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/api/endpoints.py — funciones estadisticas_grafico,
         estadisticas_distribucion, estadisticas_heatmap

Descripción:
  Variables como agrupacion, metrica, label_format, fecha_inicio y fecha_fin
  se concatenan directamente en strings SQL con f-strings sin parametrizar.
  Aunque hay validación parcial, no es suficiente para prevenir inyección.

Impacto:
  - Inyección SQL si un admin (o atacante con token) manipula la URL
  - Exposición o corrupción de la base de datos completa

Cómo arreglarlo:
  - Usar whitelist estricta de valores permitidos (comparar contra lista fija)
  - Nunca concatenar input del usuario directamente en SQL


──────────────────────────────────────────────────────────
A-5. [NECESARIO] Credenciales por defecto hardcodeadas y registradas en log
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — startup lifespan (~línea 330-355)

Descripción:
  Al arrancar, si no existen usuarios, el servidor crea:
    superadmin / admin123
    admin / admin123
  Y los registra en los logs del servidor visibles a cualquiera con acceso
  al terminal. El PIN del kiosco también tiene valor por defecto "UNASAM2025".

Impacto:
  - Si el admin no cambia las contraseñas, el sistema queda expuesto
  - Los logs revelan las credenciales en texto plano

Cómo arreglarlo:
  - Forzar cambio de contraseña en el primer inicio de sesión
  - No registrar contraseñas en los logs (ni cifradas ni en claro)
  - Exigir que las contraseñas iniciales vengan del .env


──────────────────────────────────────────────────────────
A-6. [NECESARIO] Credenciales de BD expuestas en línea de comando (mysqldump)
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/api/endpoints.py — función backup_sql

Descripción:
  mysqldump se ejecuta con --password=xxx directamente en la línea de comando,
  lo que expone las credenciales en la lista de procesos del sistema (ps, tasklist).

Impacto:
  - Credenciales de base de datos visibles para otros procesos/usuarios del sistema
  - Quedan registradas en logs del sistema operativo

Cómo arreglarlo:
  - Usar archivo ~/.my.cnf con permisos 600 (solo lectura del propietario)
  - O pasar la contraseña por stdin en lugar de argumento de línea de comando


──────────────────────────────────────────────────────────
A-7. [NECESARIO] Endpoint de backup SQL accesible a cualquier admin (no solo superadmin)
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/api/endpoints.py — función backup_sql

Descripción:
  El endpoint /admin/backup-sql requiere login pero no verifica que sea superadmin.
  Un usuario con rol 'admin' (nivel básico) puede exportar toda la base de datos.

Impacto:
  - Exportar todos los datos de alumnos, sesiones e incidencias
  - Violación de privacidad y cumplimiento normativo

Cómo arreglarlo:
  - Agregar: if admin.rol != "superadmin": raise HTTPException(403)


──────────────────────────────────────────────────────────
A-8. [NECESARIO] Token JWT pasado como parámetro en la URL del WebSocket
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (parcialmente mitigado por red local)
Archivo: admin/static/js/app.js — conexión wsAdmin

Descripción:
  El token JWT se pasa como query param en la URL:
    ws://host/ws/admin?token=eyJ...
  Queda registrado en logs del servidor, proxies y historial del navegador.

Impacto:
  - Token expuesto en cualquier proxy, load balancer o log de acceso
  - Permite robo de sesión si alguien accede a los logs

Cómo arreglarlo:
  - Enviar el token en el primer mensaje WebSocket (tipo "auth") en lugar de la URL
  - El servidor rechaza mensajes hasta recibir el auth inicial

──────────────────────────────────────────────────────────
B-1. [MEDIO] Verificación de contraseña Nivel 2 se hace en el cliente
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (feature removida, pero hash SHA-256 aún existe en código)
Archivo: server/main.py, admin/static/js/app.js

Descripción:
  El hash SHA-256 de la contraseña se enviaba al cliente para compararlo
  en JavaScript. SHA-256 sin sal es vulnerable a rainbow tables.
  Aunque el modal fue eliminado, el endpoint /api/config/nivel2-hash
  aún existe y devuelve el hash.

Impacto:
  - Si el endpoint es alcanzado, el hash puede crackearse offline en segundos
    con contraseñas comunes usando herramientas como hashcat

Cómo arreglarlo:
  - Eliminar el endpoint /api/config/nivel2-hash o restringirlo a superadmin
  - Si se reutiliza, mover la verificación al servidor con bcrypt


──────────────────────────────────────────────────────────
B-2. [MEDIO] Mensajes de actividad WebSocket sin validar origen
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (se resuelve al corregir A-1)
Archivo: server/main.py — handler tipo "actividad"

Descripción:
  Un cliente malicioso en la red puede conectarse al WebSocket de terminal
  y enviar mensajes de actividad falsos asociados a alumnos reales.

Impacto:
  - Inyectar logs de actividad falsos y generar sospechas falsas
  - Contaminar el historial de actividad del sistema

Cómo arreglarlo:
  - Al resolver A-1 (auth en WebSocket), este queda mitigado
  - Validar adicionalmente que la terminal esté registrada en BD al conectar


──────────────────────────────────────────────────────────
B-3. [MEDIO] Sin rate limiting en WebSocket de terminal (enumeración de DNIs)
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — handler login_request

Descripción:
  Hay bloqueo por intentos fallidos por terminal, pero un atacante puede
  abrir múltiples conexiones WebSocket simultáneas desde distintas IPs
  y probar DNIs en paralelo sin límite de velocidad global.

Impacto:
  - Enumeración masiva de DNIs válidos en la base de datos
  - Bypass del bloqueo por terminal

Cómo arreglarlo:
  - Rate limiting por IP: máximo N login_request por minuto por IP
  - Cerrar la conexión WebSocket tras X intentos fallidos


──────────────────────────────────────────────────────────
B-4. [MEDIO] Sin encabezados de seguridad HTTP en el panel admin
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py (respuesta HTTP general)

Descripción:
  Las respuestas del servidor no incluyen:
    - Content-Security-Policy (CSP)
    - X-Frame-Options
    - X-Content-Type-Options
    - Strict-Transport-Security (HSTS)

Impacto:
  - Clickjacking (X-Frame-Options ausente)
  - MIME sniffing (X-Content-Type-Options ausente)
  - Sin HSTS no se fuerza HTTPS aunque esté disponible

Cómo arreglarlo:
  - Agregar middleware en FastAPI que inyecte estos headers en todas las respuestas
  - Mínimo: X-Frame-Options: DENY y X-Content-Type-Options: nosniff


──────────────────────────────────────────────────────────
B-5. [MEDIO] Mensajes de error verbosos exponen detalles del sistema
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/api/endpoints.py — backup_sql (~línea 748) e import Excel (~línea 1347)

Descripción:
  Varios endpoints devuelven la excepción interna completa al cliente:
    detail=f"mysqldump falló: {stderr.decode()[:300]}"
    detail=f"Archivo Excel inválido: {e}"

Impacto:
  - Revela estructura interna del sistema, comandos usados y rutas
  - Información útil para un atacante que busca explotar el sistema

Cómo arreglarlo:
  - Registrar el error completo solo en logs del servidor
  - Devolver al cliente solo un mensaje genérico: "Error al procesar. Ver logs."


──────────────────────────────────────────────────────────
B-6. [MEDIO] Sin CSRF protection en operaciones críticas
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (mitigado parcialmente porque el JWT no está en cookies)
Archivo: admin/static/js/app.js, server/api/endpoints.py

Descripción:
  Las peticiones POST/PUT/DELETE usan el JWT en el header Authorization,
  lo que previene CSRF básico. Sin embargo, no hay token CSRF explícito.
  Si algún endpoint en el futuro usa cookies para auth, queda vulnerable.

Impacto:
  - Bajo riesgo con la implementación actual (JWT en header)
  - Riesgo alto si se migra a cookies sin protección CSRF

Cómo arreglarlo:
  - Mantener el JWT en memoria/header (no en cookies) como está actualmente
  - Documentar este requisito para no romperlo en futuras versiones


──────────────────────────────────────────────────────────
B-7. [MEDIO] Token JWT con expiración larga (8 horas) sin revocación
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/auth_service.py — ACCESS_TOKEN_EXPIRE_MINUTES = 480

Descripción:
  Los tokens duran 8 horas y no hay mecanismo de revocación.
  Si un token es robado, el atacante tiene acceso durante toda la sesión.
  Al hacer logout, el token sigue siendo válido técnicamente.

Impacto:
  - Token robado permite acceso por hasta 8 horas sin posibilidad de bloquearlo

Cómo arreglarlo:
  - Reducir expiración a 2-4 horas
  - Implementar blacklist de tokens en BD (tabla token_revocado)
  - O usar refresh tokens de corta vida


──────────────────────────────────────────────────────────
B-8. [MEDIO] PII de alumnos registrada en logs del servidor
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — múltiples líneas de logger.info()

Descripción:
  Nombres completos y DNIs de alumnos se registran en los logs del servidor
  en texto plano. Estos logs pueden ser accedidos por cualquier persona con
  acceso al servidor.

Impacto:
  - Exposición de datos personales (riesgo de cumplimiento normativo)
  - Si los logs se comparten o filtran, viola privacidad de los alumnos

Cómo arreglarlo:
  - Enmascarar DNI en logs: mostrar solo últimos 4 dígitos (****1234)
  - Enmascarar nombres: mostrar solo iniciales (J.C.P.)
  - Separar logs de auditoría (con PII) de logs operativos


──────────────────────────────────────────────────────────
B-9. [MEDIO] Contraseñas sin requisitos de complejidad
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — endpoint PUT /api/config/usuario (~línea 460)

Descripción:
  Solo se valida longitud mínima de 6 caracteres.
  No se exigen mayúsculas, números ni caracteres especiales.
  La contraseña por defecto "admin123" cumple este requisito.

Impacto:
  - Contraseñas débiles fáciles de adivinar o atacar por fuerza bruta

Cómo arreglarlo:
  - Exigir mínimo 8 caracteres, al menos 1 mayúscula y 1 número
  - Agregar validación tanto en backend como en el formulario del admin

──────────────────────────────────────────────────────────
C-1. [BAJO] Endpoints públicos del kiosco permiten enumeración de datos
──────────────────────────────────────────────────────────
ESTADO: DISEÑO INTENCIONAL, riesgo menor
Archivo: server/api/endpoints.py

Descripción:
  Los endpoints del kiosco (validar alumno, iniciar/cerrar sesión, check ban)
  son públicos por diseño. Permiten verificar si un DNI existe en la BD.

Impacto (bajo en red local):
  - Desde internet: NO alcanzable (servidor en red local)
  - Desde el WiFi de la biblioteca: posible enumeración de DNIs

Cómo mitigar (sin romper el kiosco):
  - Rate limiting: máx N intentos por IP por minuto
  - Whitelist de IPs de las PCs del laboratorio


──────────────────────────────────────────────────────────
C-2. [BAJO] IP del servidor expuesta en endpoint /api/server-info
──────────────────────────────────────────────────────────
ESTADO: DISEÑO INTENCIONAL
Archivo: server/main.py — endpoint /api/server-info

Descripción:
  Devuelve la IP local del servidor sin autenticación. Necesario para que
  los clientes descubran el servidor, pero es información útil para atacantes.

Impacto:
  - Facilita mapeo de la infraestructura de red

Cómo mitigar:
  - Requerir autenticación para el endpoint
  - O usar broadcast UDP local para descubrimiento en lugar de HTTP


──────────────────────────────────────────────────────────
C-3. [BAJO] Sin límite de tamaño en la importación de Excel
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/api/endpoints.py — endpoint de importación Excel

Descripción:
  El endpoint que importa alumnos desde Excel no tiene límite de tamaño
  de archivo. Un archivo muy grande puede agotar memoria y disco.

Impacto:
  - Denegación de servicio por agotamiento de recursos del servidor

Cómo arreglarlo:
  - Agregar validación: if file.size > MAX_SIZE: raise HTTPException(413)
  - Configurar limite en uvicorn/nginx (max_request_body_size)


──────────────────────────────────────────────────────────
C-4. [BAJO] Timeout de 60s en WebSocket puede acumular conexiones zombie
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py — WebSocket terminal, timeout=60.0

Descripción:
  Las terminales que cierran la conexión abruptamente (corte de luz, etc.)
  ocupan recursos durante 60 segundos antes de ser detectadas.
  Con muchas terminales conectadas y fallos frecuentes puede haber acumulación.

Impacto:
  - Uso innecesario de memoria y conexiones de BD
  - En escenarios de muchas PCs podría degradar el rendimiento

Cómo mitigar:
  - Mantener el heartbeat cada 3s (ya implementado en el cliente)
  - Reducir timeout a 15-20s para detectar desconexiones más rápido


──────────────────────────────────────────────────────────
C-5. [BAJO] Hash SHA-256 para nivel 2 sin sal (legado)
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (feature removida pero endpoint aún existe)
Archivo: server/main.py — /api/config/nivel2-hash

Descripción:
  El endpoint legado devuelve SHA-256 sin sal. SHA-256 sin sal es
  completamente vulnerable a rainbow tables con contraseñas comunes.

Impacto bajo porque:
  - El modal de nivel 2 fue eliminado de la interfaz
  - El endpoint requiere autenticación de superadmin

Cómo arreglarlo:
  - Eliminar el endpoint completamente ya que la feature fue removida


──────────────────────────────────────────────────────────
C-6. [BAJO] Sin auditoría de cambios de configuración
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE
Archivo: server/main.py, server/api/endpoints.py

Descripción:
  Los cambios de credenciales, configuración de backdoor y mensajes
  programados no quedan registrados con la identidad de quien los realizó.

Impacto:
  - Sin trazabilidad de quién cambió qué y cuándo
  - Dificultad para detectar cambios no autorizados

Cómo arreglarlo:
  - Agregar log con username al realizar cambios importantes:
    logger.warning(f"[AUDIT] {admin.username} cambió contraseña de {datos.rol_objetivo}")


──────────────────────────────────────────────────────────
C-7. [BAJO] Datos de alumnos en memoria sin cifrar durante sesión del cliente
──────────────────────────────────────────────────────────
ESTADO: DISEÑO INTENCIONAL, riesgo muy bajo en contexto
Archivo: client/UI/MainWindow.xaml.cs

Descripción:
  Los datos del alumno (nombre, apellidos, código) se almacenan en variables
  de memoria del proceso WPF durante la sesión activa, sin cifrar.

Impacto (muy bajo):
  - En teoría, accesible por un proceso con privilegios en la misma PC
  - En la práctica, la PC está en modo kiosco con acceso restringido

Cómo mitigar:
  - Limpiar variables al bloquear la PC (ya parcialmente implementado)
  - Usar SecureString para datos sensibles si se requiere mayor seguridad


──────────────────────────────────────────────────────────
C-8. [BAJO] Comunicación sin HTTPS/WSS (red local)
──────────────────────────────────────────────────────────
ESTADO: DISEÑO INTENCIONAL para red local
Archivo: admin/static/js/app.js, client/Services/WebSocketService.cs

Descripción:
  Todo el tráfico usa HTTP/WS sin cifrar. En red local esto tiene
  impacto reducido, pero cualquiera en la red puede capturar tráfico.

Impacto:
  - Tokens JWT y datos de alumnos visibles en la red local
  - Un alumno con Wireshark en el WiFi puede capturar sesiones

Cómo arreglarlo (a largo plazo):
  - Configurar certificado TLS autofirmado en el servidor
  - Cambiar a HTTPS/WSS en producción
