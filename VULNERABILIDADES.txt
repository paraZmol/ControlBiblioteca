A-2. [NECESARIO] SECRET_KEY de JWT débil en .env
──────────────────────────────────────────────────────────
ESTADO: ✅ RESUELTA (2026-06-03)
Archivo: server/auth_service.py:13-31, server/.env

Descripción (resuelta):
  1. El .env tenía DOS SECRET_KEY (una débil "dev_secret_key_local" y una
     fuerte duplicada). Se reescribió dejando UNA sola clave fuerte recién
     generada (token_hex(32) = 64 hex). Backup del .env anterior en .env.bak.
  2. auth_service.py ahora ENDURECIDO:
     - Si no hay SECRET_KEY → raise RuntimeError (el servidor NO arranca).
     - Si la clave es un placeholder conocido o tiene < 32 caracteres →
       raise RuntimeError. Esto evita que una clave de desarrollo llegue a
       producción y que se generen tokens con una clave temporal aleatoria.
  Verificado: el servidor carga la clave fuerte; falla correctamente con
  clave ausente o débil.

  3. El .env ESTABA trackeado en git (commiteado desde el primer commit) con
     todos los secretos. Se ejecutó `git rm --cached server/.env` para dejar
     de versionarlo (el archivo local se conserva). Se ampló .gitignore con
     `.env.*` y `server/.env.*` para cubrir backups. Verificado: .env y
     .env.bak ya no se trackean.

NOTA: La clave nueva invalida los tokens JWT previos — el admin debe volver
  a iniciar sesión tras el reinicio del servidor. Las PCs no se afectan.

PENDIENTE OPERATIVO:
  - El HISTORIAL pasado de git aún contiene los .env viejos. Como la SECRET_KEY
    ya se rotó, las claves JWT viejas quedan inservibles. PERO la contraseña de
    MySQL (impo2010) y PASS_NIVEL2 (max123) siguen en el historial — conviene
    rotarlas también si el repo es compartido o se publicará.
  - En el equipo de PRODUCCIÓN, generar una SECRET_KEY propia distinta a esta.

A-3. [NECESARIO] Verificación SSL deshabilitada en llamada al SGA UNASAM
──────────────────────────────────────────────────────────
ESTADO: ✅ RESUELTA (2026-06-03)
Archivo: server/main.py:55, 108 — función consultar_sga(dni)

Descripción (resuelta):
  Antes la consulta usaba verify=False (permitía MITM). Se verificó que el
  certificado del SGA UNASAM es VÁLIDO (prueba real: HTTP 401 con verify=True,
  sin error SSL; mismo comportamiento que con verify=False). Por tanto el
  verify=False era innecesario.
  Cambios:
    - Nueva constante _SGA_VERIFY_SSL (main.py:55), True por defecto.
    - consultar_sga ahora usa verify=_SGA_VERIFY_SSL (main.py:108).
    - Configurable vía SGA_SSL_VERIFY en .env solo para casos puntuales de
      problema de certificado (no recomendado desactivar en producción).
  Verificado: la constante resuelve a True con el .env actual.

Impacto eliminado:
  - Ya no es posible un MITM que suplante el SGA e inyecte datos falsos,
    porque el certificado del servidor se valida.

A-5. [NECESARIO] Credenciales por defecto registradas en log
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (verificado 2026-06-03)
Archivo: server/main.py:433, 445 — startup lifespan

Descripción:
  Al arrancar, si no existen usuarios, el servidor crea superadmin/admin123 y
  admin/admin123, y los REGISTRA en texto plano en el log:
    main.py:433  logger.info("Usuario superadmin creado (superadmin/admin123)")
    main.py:445  logger.info("Usuario admin creado (admin/admin123)")
  El PIN del kiosco también tiene valor por defecto.
  No se fuerza cambio de contraseña en el primer inicio de sesión.

Impacto:
  - Si el admin no cambia las contraseñas, el sistema queda expuesto
  - Los logs revelan las credenciales iniciales en claro

Cómo arreglarlo:
  - No registrar la contraseña en el log (solo "usuario X creado")
  - Forzar cambio de contraseña en el primer login
  - Idealmente, exigir contraseñas iniciales desde el .env

D-1. [MEDIO] Endpoints de procesos-ignorados sin verificación de superadmin
──────────────────────────────────────────────────────────
ESTADO: PENDIENTE (nueva — verificado 2026-06-03)
Archivo: server/api/endpoints.py:1025-1082

Descripción:
  Los 3 endpoints de procesos ignorados (GET/POST/DELETE
  /admin/procesos-ignorados) solo exigen login, NO rol superadmin:
    :1028  GET    _: Usuario = Depends(obtener_usuario_actual)
    :1047  POST   admin: Usuario = Depends(obtener_usuario_actual)  (sin check rol)
    :1071  DELETE _: Usuario = Depends(obtener_usuario_actual)
  Un admin básico puede agregar procesos a la lista de ignorados.

Impacto:
  - Un admin podría ocultar de la vista la actividad de ciertos programas.
  - Riesgo limitado: los eventos SOSPECHOSOS nunca se ocultan (siempre se
    muestran aunque su exe esté ignorado), y todo se guarda en BD igual
    (no se borra). Aun así, conviene restringir a superadmin la edición.

Cómo arreglarlo:
  - En POST y DELETE: if admin.rol != "superadmin": raise HTTPException(403)
  - GET puede quedar abierto a admin (solo lectura) o también restringirse

──────────────────────────────────────────────────────────
